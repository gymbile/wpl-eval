# wpl-eval v0.7.0 — lifecycle scenarios + Gemini coverage

Status: approved design, pre-implementation.
Base branch: `v0.7.1` (v0.6 + methodology hardening + canonical catalog vocab).
Source design sketch: `docs/V0_7_LIFECYCLE_SCENARIOS.md` (L1–L5 definitions, rationale).

## Goal

Two deliverables complete v0.7.0:

1. **Lifecycle scenarios** — measure *adaptability*: the same runtime, given an
   evolving `ClientContext`, re-shapes the served plan as the client's state
   changes mid-conversation. Five scenarios (L1–L5) from
   `V0_7_LIFECYCLE_SCENARIOS.md`.
2. **Gemini vendor coverage** — third vendor lane (deferred from v0.6 by
   commit `1e3178b`), mirroring the Anthropic adapter added in v0.6.

Out of scope: clinician review of the scenario corpus — deferred to the next
release (v0.8); new lifecycle scenarios carry `[VERIFY]` markers per corpus
convention until then. Also out of scope: the full paid
corpus sweep (implementation + smoke run only; the sweep is a separate
decision after smoke results are reviewed).

## Approach

Extend the existing multi-turn machinery in place (approach A). Lifecycle
scenarios are multi-turn scenarios with two optional fields; absent fields
mean zero behaviour change, following the `block_purpose` precedent that kept
v0.5/v0.6 numbers frozen. No new runner phase, no forked turn loop —
`runLaneBMulti` / `runLaneAMulti` and latest-valid-turn semantics are reused
as-is.

## 1. Scenario schema (`src/lib/types.ts`, `scenarios/scenarios.yaml`)

Two new optional fields on `Scenario`:

```ts
turn_states?: Array<{
  turn: number;                        // 1-based; state applies from this turn onward
  context?: Partial<ClientContext>;    // deep-merged over base ClientContext
  rules?: Scenario["rules"];           // REPLACES the active rule set from this turn on
}>;

lifecycle_criteria?: Array<{
  id: string;                          // stable label for the report matrix
  from_turn: number;                   // applies to plans served at turns >= from_turn
  to_turn?: number;                    //   ... and <= to_turn (default: last turn)
  weeks?: { from: number; to: number }; // which weeks of the served plan (default: all)
  must_not_contain?: string[];         // exercise slugs (canonical catalog vocab)
  must_eventually_contain?: string[];  // progression check: appears in >=1 qualifying plan
  rpe_max?: number;                    // intensity cap across qualifying weeks
}>;
```

Semantics:

- The trainer's per-turn messages stay in `multi_turn[]` exactly as today.
  `turn_states` carries only the state, keyed to the same 1-based turn
  indices.
- **Context merge**: the active context at turn *t* is
  `buildClientContext(scenario)` shallow-merged with every
  `turn_states[i].context` where `turn_states[i].turn <= t`, in ascending
  turn order (later overlays win per top-level key; `cycle` is replaced
  wholesale when present, not deep-merged — a cycle state change is always a
  full re-description).
- **Rules replacement**: when a turn state carries `rules`, it *replaces* the
  active rule set from that turn onward (not merges). Replacement makes
  regression (L4) and clearance (L1, L2) expressible without a rule-removal
  syntax. A turn state without `rules` leaves the previous set active.
- `must_eventually_contain` passes if the slug appears in at least one
  qualifying (turn-range × week-range) served plan; it is evaluated once over
  the whole conversation and emits at most one violation per slug.

Load-time validation (fail loud, before any LLM call):

- every `turn_states[].turn` and criteria turn bound within
  `1..multi_turn.length`, strictly ascending turn order in `turn_states`;
- every slug in `must_not_contain` / `must_eventually_contain` and in every
  rule action present in the canonical exercise vocab;
- `lifecycle_criteria` present iff `turn_states` present.

## 2. Runner state injection (Lane B)

`runOnce()` in `src/lanes/lane-b.ts` gains an optional `ctx: ClientContext`
and `rules: Rule[]` parameters (defaulting to today's scenario-derived
values). `runLaneBMulti` computes the active context + active rule set per
turn (per the merge/replacement semantics above) and passes them in, so
`enforce()` fires with the state the runtime would hold at that moment.

Lane A gets **no injection** — the raw LLM sees only the conversation text.
That asymmetry is the measurement: Lane B's governance layer receives
structured state; Lane A must track it from prose alone.

Flare-window plumbing (`perDayExtraForbids`) keeps working: it derives from
the *active* rule set + *active* context per turn instead of the static
scenario fields.

## 3. Scoring (`src/scoring/lifecycle.ts`, new)

Pure function:

```ts
scoreLifecycle(scenario: Scenario, perTurnPlans: ExtractedPlan[]): Violation[]
```

- Exits `[]` immediately when `lifecycle_criteria` is absent — frozen
  v0.5/v0.6 results stay frozen.
- For each criterion, for each turn in `[from_turn, to_turn]` that has an
  extracted plan: filter the plan's exercises to the criterion's week range,
  match `must_not_contain` slugs through the existing blacklist matcher
  (stemming + compound-plural handling), check `rpe_max` against extracted
  intensities in-range.
- `must_eventually_contain`: after the per-turn pass, one violation per slug
  never observed in any qualifying plan.
- New `Violation` kinds:
  - `lifecycle_forbidden` — state-conditional blacklist hit (item, week, turn in `detail`)
  - `lifecycle_regression_missing` — `must_eventually_contain` never satisfied
  - `lifecycle_intensity` — `rpe_max` exceeded
- Wired into `runLaneAMulti` and `runLaneBMulti`, appended to the final
  violations list (both lanes already persist `extracted_plans_per_turn`).
  For turns that produced no valid plan (Lane B non-compiling turn), the
  turn is skipped by the scorer — non-service is already captured by
  `wpl_valid` / latest-valid-turn, and double-counting it as a lifecycle
  violation would conflate failure modes.

## 4. Report (`src/report.ts`)

- Lifecycle scenarios join the headline table like any other scenario.
- New adaptation-matrix section, rendered only when the result set contains
  lifecycle scenarios: one table per scenario — rows = criteria (by `id`),
  columns = model × lane, cells = pass/fail.

## 5. Scenario corpus (L1–L5)

Author the five scenarios from `V0_7_LIFECYCLE_SCENARIOS.md` in
`scenarios/scenarios.yaml`, ids:

| id | design-doc name | key failure mode tested |
|---|---|---|
| `lifecycle_injury_return` | L1 acute injury → recovery → clearance | exercise toggle: forbidden → allowed |
| `lifecycle_postpartum_gate` | L2 postpartum clearance gate | historical constraints in consolidated plan |
| `lifecycle_travel_deload` | L3 travel pause → resumption | detraining requires regression, not continuation |
| `lifecycle_cardiac_phases` | L4 cardiac progression AND regression | state *tightening* handled, not just loosening |
| `lifecycle_cycle_transition` | L5 irregular → regular cycle | projection re-anchoring mid-programme |

Authoring constraints:

- 8-turn `multi_turn` conversations in trainer voice, matching the corpus
  style.
- All slugs from the canonical catalog vocab
  (`src/scoring/matcher-vocab.generated.ts` / `@gymbile/wpl-ai` exercise list).
- L4's HR-cap phases are approximated with `rpe_max` (WPL prescriptions
  carry RPE, not HR) — stated in the scenario's `safety_rationale`.
- L3's deload check (volume −20–30%) reuses the v0.6 short-plan volume
  machinery where practical; if a per-week volume comparison across turns
  proves too fragile for v0.7.0, the deload check ships as
  `must_eventually_contain`-style presence checks plus `rpe_max`, and the
  volume-delta check is noted as future work in the scenario comments.
- Each scenario carries `safety_rationale` with clinical citations,
  `[VERIFY]` markers where drafted from non-clinical reading (matching
  corpus convention; clinician review is the v0.7 follow-up).

## 6. Gemini vendor coverage

- `src/models/gemini.ts` — adapter mirroring `src/models/anthropic.ts`
  (~90 lines): `@google/genai` SDK (one new dependency), `GEMINI_API_KEY`
  required via `src/lib/env.ts`, temperature 0, `max_output_tokens` mapped,
  same refusal-marker heuristic so `refusal` stays cross-vendor comparable.
  Text extracted from candidate parts; token counts from `usageMetadata`.
- Models (flagship / mid / cheap, mirroring both existing vendors):
  `gemini-2.5-pro`, `gemini-2.5-flash`, `gemini-2.5-flash-lite`. Exact IDs
  and pricing rows verified against Google's published price table at
  implementation time and dated in `src/lib/pricing.ts` comments, matching
  the OpenAI/Anthropic row convention.
- `src/lib/types.ts`: `GeminiModel`, `LockedModelV07 = LockedModelV06 | GeminiModel`.
- `src/runner.ts`: `LOCKED_MODELS_V0_7` (10 models), `--sweep=v0.7`,
  `gemini-` prefix dispatch in `makeModel`.
- Tests mirroring the Anthropic scaffold tests: message mapping, refusal
  detection, pricing presence for all three models, sweep membership.

## 7. Error handling

Fail loud, never score silently-misconfigured trials (existing posture):

- Scenario load-time validation failures (§1) throw before any API call.
- `enforce()` diagnostics with per-turn rules throw, as today.
- A lifecycle scenario run with `--phase=single` throws (`lifecycle
  scenarios are multi-turn only`) rather than silently measuring nothing.

## 8. Testing

Unit (vitest, no network):

- overlay merge: ascending application, later-wins, `cycle` replaced
  wholesale, rules replacement vs retention;
- `scoreLifecycle` on synthetic per-turn plans: toggle (L1 shape),
  consolidated-history (L2 shape), regression (L4 shape),
  `must_eventually_contain` pass + fail, week-range filtering, `rpe_max`;
- guard: scenario without `lifecycle_criteria` → zero lifecycle violations;
- corpus lint: every slug in lifecycle scenarios' criteria and rules exists
  in the canonical vocab; turn indices valid;
- Gemini adapter tests (§6);
- existing suite stays green.

Smoke run (live, cheap):

```
npm run runner -- --scenario=lifecycle_injury_return --phase=multi \
  --model=gpt-5-mini --out=results-v0.7-smoke
npm run runner -- --scenario=lifecycle_injury_return --phase=multi \
  --model=gemini-2.5-flash --out=results-v0.7-smoke
```

Both lanes, then `report` over `results-v0.7-smoke` to verify the adaptation
matrix renders. Full 5-scenario × 10-model sweep is a separate post-review
decision (~$15–25 estimated in the design doc).

## 9. Non-goals / freeze guarantees

- No change to any existing scenario, lane logic for non-lifecycle
  scenarios, or scoring of existing result files. `rescore.ts` untouched.
- No Gemini rows added to v0.5/v0.6 published tables; Gemini appears only
  under `--sweep=v0.7` or explicit `--model=`.
- `package.json` version stays as-is until release tagging (tags, not the
  private package version, carry eval versioning).
